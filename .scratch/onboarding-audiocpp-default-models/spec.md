# Онбординг: дефолтные модели audio.cpp вместо Parakeet

Status: resolved

## Problem Statement

Новый пользователь на шаге «Getting things ready» онбординга по умолчанию скачивает модель Parakeet (англоязычный ASR) и рекомендованную summary-модель. При этом стратегический движок транскрибации приложения — audio.cpp: GigaAM v3 e2e CTC (русская речь), уже внедрён как провайдер `audioCpp`, а модель диаризации Nemotron-3 Diarization в онбординге не скачивается вовсе (см. `.scratch/audio-cpp-provider/spec.md`, ADR-0001). Пользователь вынужден после онбординга лезть в настройки, скачивать GigaAM отдельно и остаётся без меток спикеров, а скачанный Parakeet ему не нужен — тратится ~670 МБ трафика и диска впустую.

## Solution

На шаге «Getting things ready» по умолчанию скачиваются три модели:

1. **GigaAM v3 e2e CTC** (`gigaam-v3-e2e-ctc-f16`) — обязательная, активность кнопки Continue зависит от неё (как сейчас от Parakeet).
2. **Nemotron-3 Diarization** (`nemotron-3-diarization-bf16`) — качается параллельно в фоне, на Continue не влияет (как сейчас summary-модель).
3. **Qwen 3.5 4B** — summary-модель, текущий поток рекомендации (`builtin_ai_get_recommended_model`) не меняется.

Parakeet при онбординге больше не скачивается. По завершении онбординга конфигурация транскрибации указывает на провайдера `audioCpp` с моделью GigaAM v3 e2e CTC — запись доступна сразу, без визита в настройки.

## User Stories

1. Как новый пользователь, я хочу, чтобы при первом запуске скачивалась модель GigaAM v3 e2e CTC, чтобы русские встречи транскрибировались качественно сразу после онбординга.
2. Как новый пользователь, я хочу, чтобы модель Nemotron-3 Diarization скачивалась по умолчанию, чтобы видеть, кто что говорил, без ручной настройки.
3. Как новый пользователь, я хочу, чтобы summary-модель Qwen 3.5 4B скачивалась по умолчанию, чтобы саммари работали сразу после онбординга.
4. Как новый пользователь, я хочу, чтобы Parakeet не скачивался, чтобы не тратить трафик и место на диске на модель, которая мне не нужна.
5. Как новый пользователь, я хочу видеть на шаге «Getting things ready» отдельные карточки для модели транскрибации и модели диаризации, чтобы понимать, что именно скачивается.
6. Как новый пользователь, я хочу, чтобы кнопка Continue оставалась неактивной, пока не скачана модель транскрибации (GigaAM), чтобы не попасть в приложение без работающего распознавания речи.
7. Как новый пользователь, я хочу, чтобы недокачанная модель диаризации не блокировала Continue, чтобы не ждать лишних гигабайт при медленном канале.
8. Как новый пользователь, я хочу видеть прогресс скачивания каждой модели в мегабайтах и процентах, чтобы оценить оставшееся время.
9. Как новый пользователь, я хочу, чтобы после завершения онбординга запись работала сразу, без настройки движка транскрибации в настройках.
10. Как новый пользователь, я хочу, чтобы после завершения онбординга в транскрипте встречи были метки спикеров (после докачки модели диаризации), чтобы понимать, кто говорил.
11. Как новый пользователь, я хочу кнопку «Try Again» при ошибке скачивания любой из моделей, чтобы перезапустить загрузку без перезапуска онбординга.
12. Как новый пользователь, я хочу, чтобы скачивание продолжалось в фоне при переходе дальше, чтобы не ждать у экрана.
13. Как вернувшийся пользователь (онбординг не завершён, приложение перезапущено), я хочу, чтобы онбординг возобновился с корректного шага и докачал недокачанные модели audio.cpp, а не искал Parakeet.
14. Как существующий пользователь (онбординг завершён ранее), я хочу, чтобы мой прогресс и конфигурация сохранились, а онбординг не запускался заново.
15. Как пользователь macOS, я хочу, чтобы после скачивания моделей шёл шаг разрешений, как и сейчас.
16. Как пользователь, я хочу, чтобы размеры моделей на карточках соответствовали каталогу, а не были захардкожены устаревшие значения.
17. Как разработчик, я хочу, чтобы код онбординга не ссылался на Parakeet вообще, чтобы не было двойственности «качаем одно, настраиваем другое».
18. Как разработчик, я хочу, чтобы событие прогресса скачивания audio.cpp-моделей несло те же поля, что и у Parakeet/builtin-ai (downloaded_mb, total_mb, speed_mbps), чтобы UI-пайплайны остались единообразными.
19. Как пользователь с медленным каналом, я хочу, чтобы докачка моделей после онбординга не мешала начать пользоваться приложением, как и сейчас.

## Implementation Decisions

- **Шаг «Getting things ready» (frontend)**: карточка «Transcription Engine» (~670 MB, Parakeet) заменяется на карточку GigaAM v3 e2e CTC (размер из каталога); добавляется карточка «Speaker Diarization» (Nemotron-3, статус-колонка как у summary-модели — не блокирует). Карточка summary-модели и весь поток `builtin_ai_get_recommended_model` / `resolveOnboardingSummaryModelStatus` не меняются.
- **Гейт Continue**: только GigaAM. В `handleContinue` проверка `parakeet_init` + `parakeet_has_available_models` заменяется на `audiocpp_model_init` + `audiocpp_has_transcription_model` — строгий ASR-гейт: установленная только модель диаризации его не удовлетворяет (контракт команды уже зафиксирован и протестирован).
- **Старт загрузок**: `startBackgroundDownloads` в OnboardingContext меняет контракт опций — вместо `includeParakeet` флаги на загрузку моделей транскрибации и диаризации audio.cpp (например `includeAudioCppTranscription` / `includeAudioCppDiarization`); вызовы — `audiocpp_download_model` с именами `gigaam-v3-e2e-ctc-f16` и `nemotron-3-diarization-bf16` (имена — константы рядом с текущим `PARAKEET_MODEL`, по образцу имен в каталоге).
- **События прогресса**: слушатели переключаются с `parakeet-model-download-*` на `audiocpp-model-download-progress|complete|error` (payload уже содержит `modelName` — фильтрация по имени модели сохраняется). Payload `audiocpp-model-download-progress` расширяется полями `downloaded_mb`, `total_mb`, `speed_mbps` — по форме событий Parakeet/builtin-ai. `total_mb` бэкенд берёт из каталога (`ModelSpec.size_mb`), скорость считает при эмиссии прогресса.
- **Повторная попытка**: `parakeet_retry_download` заменяется на повторный вызов `audiocpp_download_model` (отдельной retry-команды у audio.cpp нет; скачивание и есть идемпотентный вход).
- **Возобновление**: `checkActiveDownloads` использует `audiocpp_get_available_models` вместо `parakeet_get_available_models`; детект активной загрузки — по `ModelStatus::Downloading` из статуса модели.
- **Состояние контекста**: `parakeetDownloaded` / `parakeetProgress` / `parakeetProgressInfo` и сеттеры переименовываются в нейтральные (`transcriptionModelDownloaded`, `diarizationModelDownloaded` и т.п.) — состояния моделей транскрибации и диаризации раздельные.
- **Завершение онбординга (Rust)**: `complete_onboarding` сохраняет конфигурацию транскрибации через `SettingsRepository::save_transcript_config` с провайдером `audioCpp` и моделью `gigaam-v3-e2e-ctc-f16` вместо `parakeet` / `DEFAULT_PARAKEET_MODEL`. Модель диаризации в конфиг не пишется — она резолвится автоматически из установленных каталожных моделей (`select_diarization_model`).
- **Схема onboarding-status.json — полная замена** (решение пользователя): поле `model_status.parakeet` удаляется, вместо него поля под модели audio.cpp (транскрибация, диаризация) + существующие `summary` / `selected_summary_model`. Старый JSON десериализуется без ошибок (неизвестные поля игнорируются, новые — default «not_downloaded»), затем статус всё равно верифицируется по диску через audioCpp-менеджер, как сейчас. Пользователи с `completed: true` не затрагиваются — завершённый статус доверяется без повторного показа онбординга; попавшие на шаг загрузки со старым статусом просто увидят, что GigaAM не скачан, и скачают его.
- **Размеры на карточках**: захардкоженное `~670 MB` и `totalMb: 670` уходят; размеры берутся из каталога/событий (GigaAM и Nemotron из `ModelSpec.size_mb`).
- **Провайдер по умолчанию при отсутствии конфига**: существующие fallback-ветки в диспетчере транскрибации (defaulting to parakeet при отсутствии TranscriptConfig) в рамках этой задачи не меняются — онбординг после изменения всегда пишет конфиг `audioCpp`.

## Testing Decisions

- **Хороший тест** проверяет внешнее поведение через шов, а не детали реализации: на входе — события прогресса/статусы моделей, на выходе — разрешённость Continue, корректные статусы карточек, сохранённая конфигурация провайдера.
- **Шов 1 — Rust `onboarding.rs`**: юнит-тесты serde-совместимости схемы статуса (аналог существующего `onboarding_status_deserializes_without_selected_summary_model`): старый JSON с `parakeet`-полем десериализуется в новую схему со значениями по умолчанию; новый JSON сериализуется с новыми полями. Поведение `complete_onboarding` (что пишется в `save_transcript_config`) — через мок/инспекцию репозитория на уровне существующих Rust-тестов настроек, если таковые есть; иначе минимальный тест маппинга «onboarding → provider/model».
- **Шов 2 — чистые frontend-хелперы** (приоритетное искусство: `frontend/tests/lib/onboarding-summary-model.test.mjs`): резолверы статусов/разрешённости Continue выносятся в `frontend/src/lib/` чистыми функциями (вход: статусы трёх моделей; выход: disabled/enabled Continue, waiting/downloading/completed по карточкам) и покрываются табличными тестами — включая кейсы «диаризация упала, Continue активна» и «GigaAM упала, Continue неактивна».
- **Шов 3 — событие прогресса**: Rust-тест формы payload `audiocpp-model-download-progress` (поля percent + mb/speed присутствуют, `status` переходит в `completed` на 100) по образцу существующих юнит-тестов `audio_cpp_engine`.
- **Ручная верификация**: прогон онбординга в Tauri-приложении (`pnpm run tauri:dev`) на чистом профиле — три модели качаются, Continue ждёт только GigaAM, после завершения запись работает на `audioCpp`, в новой встрече после докачки Nemotron появляются метки спикеров. Плюс перезапуск посреди скачивания (возобновление шага).

## Out of Scope

- Удаление движка Parakeet из приложения — движок и его настройки остаются, переключение на него в Settings по-прежнему возможно.
- Миграция конфигурации транскрибации у существующих пользователей с `parakeet` на `audioCpp` — их SQLite-конфиг не трогаем, меняется только то, что пишет онбординг.
- Изменение логики рекомендации summary-модели (порог RAM для Qwen 3.5 4B vs 2B остаётся как есть).
- Whisper-пути онбординга (их нет и не добавляется).
- Отображение меток спикеров и сама диаризация — уже реализованы (`.scratch/audio-cpp-provider`), здесь только дефолтное скачивание модели.

## Further Notes

- Summary-модель: рекомендация `builtin_ai_get_recommended_model` на системах от 16 ГБ RAM — `qwen3.5:4b` (Qwen 3.5 4B), ниже порога — `qwen3.5:2b`; пользователь подтвердил, что текущий поток сохраняем.
- Копирайт шага «You can start using Samobranka after downloading the Transcription Engine.» остаётся валидным — обязательной остаётся только модель транскрибации.
- Имена моделей — единственный источник истины каталог `audio_cpp_engine::catalog`; фронтенд дублирует их константами по образцу существующего `PARAKEET_MODEL` (как уже сделано в менеджере моделей audio.cpp).
- GigaAM F16 и Nemotron BF16 — единственные каталожные варианты на свои задачи; «выбор модели» на шаге загрузки не предусмотрен, как и сейчас для Parakeet.

## Update 2026-11-18: обоснование дефолтов пересмотрено

Диаризация больше не привязана к провайдеру транскрибации ([ADR 0004](../../docs/adr/0004-diarization-independent-of-transcription-provider.md), спека `.scratch/diarization-provider-decoupling/`): проход выполняется при установленной модели Nemotron независимо от того, чем транскрибирована встреча, а модель диаризации управляется в собственной секции настроек, видимой при любом провайдере.

Что из этого следует для этого решения:

- **Аргумент «иначе у пользователя не будет диаризации» больше не действует.** Пользователь Parakeet после скачивания Nemotron получит метки спикеров, не меняя движок распознавания.
- **Дефолты онбординга при этом не меняются.** Скачивание GigaAM и Nemotron по умолчанию и провайдер `audioCpp` в завершении онбординга сохраняются, но обоснование теперь другое: GigaAM — стратегический движок для русской речи, а Nemotron скачивается потому, что новый пользователь не должен догадываться о существовании отдельной секции настроек, чтобы увидеть спикеров. Плюс онбординг остаётся единственным местом, где модели ставятся заранее, а не по факту неудачного прохода.
- **Требование «диаризация не блокирует Continue» остаётся в силе** и теперь ещё логичнее: без модели транскрипт всё равно сохраняется, просто без меток.
