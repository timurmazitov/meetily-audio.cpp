# Синхронизация с upstream Meetily v0.5.0 и починка релизной валидации

## Problem Statement

Владелец форка Samobranka не может выпускать релизы и не может безопасно обновляться с upstream.

**Релизы не проходят валидацию.** Job `validate-release` в `.github/workflows/release.yml` безусловно читает `tauri.conf.json["plugins"]["updater"]["pubkey"]`, но ADR 0002 удалил секцию `plugins.updater` при отключении автообновления. Проверка падает с `KeyError` ещё до сверки ассетов. Та же проверка требует ровно по одному `*.dmg`, `*.app.tar.gz`, `*.msi`, `*-setup.exe`, `*.deb`, `*.AppImage` **и валидную minisign-подпись** для всех, кроме dmg, — а в конфиге стоит `createUpdaterArtifacts: false`, то есть updater-артефактов и их `.sig` не будет. Следующий job `release-summary` зависит от `validate-release` и скачивает `latest.json`, которого при отключённом updater тоже не существует, — падение каскадом.

**Форк не получает исправления сборки из v0.5.0.** Его база — merge-коммит upstream `release-v0.5.0`, но пять коммитов между этим merge и тегом `v0.5.0` не влиты. Из-за этого:

- `llama-helper` собирается с OpenSSL, и на macOS-раннерах с Homebrew OpenSSL 4 сборка падает: `llama-cpp-sys-2 =0.1.146` не компилируется против нового заголовка (`X509_get_subject_name` возвращает `const X509_NAME *`);
- все build-workflow используют `dtolnay/rust-toolchain@stable`, а Rust 1.100 стабилизировал новый build-dir layout: `tauri-build 2.6.1` и `ort 2.0.0-rc.10` в `Cargo.lock` форка те же, что падают (Linux — `IsADirectory` при копировании сайдкара, Windows — path not found на `DirectML.dll`);
- `validate-release` гоняется на `ubuntu-22.04`, где `minisign` не упакован.

**Нет зафиксированного способа обновляться.** Прошлая синхронизация была сделана так, что факт её существования неочевиден: база форка — upstream-merge внутри истории, теги upstream отсутствуют, `upstream`-remote не настроен, и повторная синхронизация каждый раз требует заново выяснять, что уже влито, а что нет.

## Solution

Одна разовая процедура синхронизации плюс один постоянный шов на релизную валидацию.

**Синхронизация.** В репозиторий добавляется `upstream`-remote, вливаются два диапазона:

1. тег `v0.5.0` — CI-фиксы сборки (OpenSSL-фри `llama-helper`, пин Rust 1.99.1, `validate-release` на Ubuntu 24.04), слияние проходит без конфликтов;
2. `upstream/main` (три пост-теговых коммита) — структура README и примечание про glibc для Linux; два конфликта, оба про бренд.

Содержательная часть релиза v0.5.0 (119 файлов: Linux-аудио через PulseAudio, `StopOutcome`, `AudioDevice.label`, `tauri-plugin-log`, Parakeet v3 с HuggingFace) в форке **уже есть** и перебрендирована — она пришла вместе с merge-коммитом `release-v0.5.0`. Аудит зафиксирован в `docs/research/upstream-0.5.0.md`.

**Релизная валидация.** Логика проверки ассетов и сборки манифеста выносится из inline-heredoc в workflow в отдельный исполняемый скрипт, который знает два режима: автообновление выключено (сейчас) и включено (будущее, ADR 0002). В выключенном режиме проверяются только факты о пакетах; манифест `latest.json` и minisign-верификация не выполняются и не упоминаются в сводке. Во включённом — выполняются ровно как сейчас. Режим определяется наличием `plugins.updater.pubkey` в конфиге, без отдельного флага в workflow.

## Implementation Decisions

**Состав синхронизации — зафиксированные факты.**

- База форка (первый форк-коммит) имеет родителем upstream-merge `release-v0.5.0`, который является предком тега `v0.5.0`. Следствие: `diff <база>..v0.5.0` — это 10 файлов CI/скриптов, и только они отсутствуют в форке.
- Вливается в два приёма и двумя отдельными merge-коммитами: сначала тег `v0.5.0`, затем `upstream/main`.
- Конфликтов при слиянии тега нет. При слиянии `upstream/main` — ровно два: README и конфиг бандла.

**Разрешение конфликтов — правило «бренд побеждает, структура берётся».**

- README: сохраняется раздел установки Samobranka со ссылками на репозиторий владельца; из upstream берётся структура (Windows и macOS одной таблицей) и примечание про glibc 2.35 для Linux. Строка установки через upstream-скрипт и upstream-ссылки на релизы не переносятся.
- Конфиг бандла: сторона форка принимается целиком (описания продукта, publisher, homepage). Формулировки upstream про «note taker» и «Meetily Community Edition» не принимаются.
- `scripts/install-linux.sh` в форк **не переносится**: он адресует upstream-репозиторий, чужие пути данных и чужой идентификатор приложения. Перебрендированный установщик — отдельная работа.

**Сборочные фиксы, которые принимаются из upstream целиком.**

- `llama-helper` собирается с отключённым поиском OpenSSL через переменную CMake в окружении сборки: и в workflow, и в локальных скриптах сборки/дева GPU-варианта.
- Все build-workflow пинят тулчейн на конкретную версию вместо `stable`. Пин оправдан локом форка (`tauri-build 2.6.1`, `ort 2.0.0-rc.10`); снимать его — только вместе с обновлением этих зависимостей.
- `validate-release` переезжает на образ, где `minisign` доступен из пакетного менеджера.

**Релизная валидация: новый шов.**

- Вся логика из inline-Python в workflow выносится в самостоятельный исполняемый скрипт в каталоге скриптов репозитория. Workflow вызывает его одной строкой и передаёт: каталог с ассетами, версию, `owner/repo`. Скрипт не импортирует проектный код и не знает про GitHub API — на вход получает уже скачанные файлы.
- Режим определяется наличием секции `plugins.updater.pubkey` в конфиге бандла; публичный ключ передаётся в скрипт файлом.
  - **Автообновление выключено (текущее состояние):** проверить, что каждый ожидаемый тип пакета присутствует ровно в одном экземпляре; подписи не проверять; манифест не создавать; напечатать явную строку о том, что автообновление выключено (ADR 0002) и манифест пропущен.
  - **Автообновление включено:** к этому добавляются требование `.sig` для подписываемых типов, minisign-верификация и сборка `latest.json` в том же формате, что сейчас (platforms-маппинг по типам пакетов).
- Ожидаемый список типов пакетов задаётся одной таблицей «тип → glob → подписывается ли», чтобы правка конфига бандла была правкой одной строки.
- Ошибки — человекочитаемые, с перечислением найденных файлов: «ожидался ровно один X, найдено N». Ненулевой код возврата.
- Вызов minisign изолируется в одну функцию, чтобы её можно было подменить в тестах без поднятия настоящего ключа.

**Согласование пайплайна с ADR 0002.**

- Job сводки релиза больше не требует существования `latest.json`: если манифеста нет, блок с его содержимым пропускается, сводка строится по списку ассетов релиза.
- Тексты сводки перестают утверждать, что `.sig` и `latest.json` загружены, когда автообновление выключено; упоминание ручной S3-загрузки остаётся только как указание на будущую работу со ссылкой на ADR.
- Поведение «не релизить на существующем теге» сохраняется.

**Brand-гейт.**

- Существующий brand-lint остаётся единственным гейтом на проникновение upstream-бренда; новый гейт не добавляется.
- В его allowlist добавляется исследовательский документ про upstream (имя upstream в нём — предмет исследования, а не регресс бренда).
- Allowlist исключений перестаёт сравнивать только имя файла и начинает принимать путь целиком, иначе исключение по пути невыразимо.

**Чего не меняем.**

- Схема БД и миграции: релиз v0.5.0 их не менял, синхронизация их не трогает.
- Ни одна Tauri-команда, событие или payload не меняются этой работой.
- Версия приложения остаётся 0.5.0; нумерация и первый публичный релиз — вне этой спеки.

## Testing Decisions

**Что считается хорошим тестом здесь.** Проверяется внешнее поведение шва: на входе — каталог с файлами и наличие/отсутствие публичного ключа, на выходе — код возврата, текст ошибки и (когда режим включён) содержимое `latest.json`. Не проверяются внутренние функции, порядок обхода каталога, форматирование логов. Форма workflow-файлов тестами не покрывается: такой тест хрупок и ловит правку YAML, а не поведение.

**Шов 1 (существующий, расширяется): brand-lint по репозиторию.** Прогоняется после каждого merge-коммита и на чистом дереве. Это единственная автоматическая проверка того, что синхронизация не вернула upstream-бренд. Прецедент: этот же скрипт уже используется как регресс-гейт ребрендинга.

**Шов 2 (новый, единственный): CLI скрипта релизных ассетов.** Тесты — модульные, на стандартной библиотеке языка скрипта (внешних зависимостей не добавляем: в репозитории нет тест-раннера для корневых скриптов, а ставить пакетный менеджер ради одного скрипта не оправдано).

Покрываемые случаи:

1. полный комплект пакетов без публичного ключа → успех, манифест не создан;
2. отсутствует один тип пакета → ошибка с именем отсутствующего типа;
3. два пакета одного типа → ошибка с указанием дубля;
4. публичный ключ присутствует, `.sig` есть у всех подписываемых → успех, `latest.json` создан с корректным `version` и полным набором платформ;
5. публичный ключ присутствует, у одного пакета нет `.sig` → ошибка;
6. верификация подписи провалилась → ошибка (через подменённую функцию minisign, без настоящего ключа).

Фикстуры — пустые файлы с правильными именами во временном каталоге; тесты не пишут в репозиторий.

**Ручная верификация, которую тесты не заменяют.**

- После каждого merge: прогон brand-lint, проверка, что в слитых workflow одновременно живы fork-only шаги (staging рантайма audio.cpp, `SAMOBRANKA_*` секреты) и upstream-фиксы (отключённый OpenSSL, пин тулчейна).
- `cargo check` в Rust-крейте и проверка типов фронтенда — как обычно для изменений в репозитории.
- Сборка в Tauri для проверки, что приложение стартует.
- Реальный прогон `Release` workflow невозможен локально: проверка того, что macOS-сборка проходит на OpenSSL 4, и что Tauri при `createUpdaterArtifacts: false` действительно не выпускает `.sig` и `.app.tar.gz`, остаётся **неподтверждённой** до первого прогона на GitHub-раннерах.

**Прецеденты в репозитории.** Для скриптов в корне — `scripts/check-brand.py` (Python, без зависимостей, запускается вручную). Для чистых функций — `frontend/tests/lib/onboarding-summary-model.test.mjs` (табличные кейсы на вход/выход). Для Rust — модульные тесты рядом с кодом, прогон `cargo test --lib`.

## Out of Scope

- Перебрендированный Linux-установщик (однострочная установка, `--uninstall`/`--purge`, десктоп-файл). Отдельная работа: требует собственного `REPO`, путей под `ai.samobranka.app` и имён ассетов форка.
- Повторное включение автообновления: собственный endpoint, новая пара minisign-ключей, возврат capability и permission. Отдельная работа по ADR 0002; эта спека только делает шов готовым к включению.
- Создание секретов и переменных в настройках GitHub-репозитория.
- Повышение версии приложения и публикация первого релиза.
- Любые изменения в движках транскрибации, диаризации, онбординге и summary: upstream их в этом диапазоне не трогал, и эта работа их не касается.
- Перенос остальной upstream-документации, не затронутой конфликтом README.

## Further Notes

- Полный аудит релиза (группы изменений по коммитам, список ломающих изменений, что уже есть в форке) — `docs/research/upstream-0.5.0.md`. Спека не дублирует хеши и PR-номера, чтобы они не устарели в двух местах.
- Ловушки, выявленные при аудите и релевантные после синхронизации: переменная включения отладочных логов в форке называется `SAMOBRANKA_DEBUG_LOG`, а не upstream-имя; сужение `assetProtocol.scope` до каталога doodle унаследовано форком и является текущим поведением, а не риском merge.
- На момент написания спеки рабочее дерево содержит незакоммиченное изменение README (удаление встраиваемых изображений) — оно принадлежит владельцу и не должно быть потеряно при слиянии: merge тоже трогает этот файл, поэтому локальную правку нужно зафиксировать или отложить до merge.
- Ожидаемая последовательность: слияние тега → слияние upstream/main → правка релизной валидации. Порядок важен только для первых двух (второе опирается на первое); починка валидации независима.
